# PRD: 코딩테스트 데일리

## 1. 개요
목표 기업(네이버, 카카오, 쿠팡·배민·당근·토스, 삼성·현대·SK)의 코딩테스트 출제 경향에 맞춘 대표 문제를 매일 웹 푸시 알림으로 받아보고, 아이폰 홈 화면에서 앱처럼 사용할 수 있는 PWA(Progressive Web App)이다. 사용자별로 알림 시간, 요일, 기업/알고리즘/난이도 필터, 출제 순서를 자유롭게 설정할 수 있고, 새 문제는 GitHub PR을 통해 검토 후 반영하는 방식으로 여러 사람이 함께 채워나갈 수 있다.

## 2. 배경 및 문제 정의
코딩테스트는 기업마다 자주 나오는 유형과 평가 포인트가 다르다. 목표 없이 무작위로 문제를 풀면 실제 시험에서 낯선 유형에 시간을 뺏기거나, 정작 자주 나오는 유형에 대한 숙련도가 부족한 채로 시험에 임하게 된다. 또한 "매일 한 문제씩 꾸준히 푼다"는 계획은 세우기는 쉬워도 실천이 어렵고, 기존 코딩테스트 연습 서비스들은 알림을 특정 시간에 개인화해서 보내주거나 기업별 경향에 맞춰 문제를 골라주지 않는다.

## 3. 목표
- 매일 정해진 시간에 목표 기업 유형에 맞는 문제를 놓치지 않고 받아본다
- 준비 중인 기업이 여러 곳이어도 각각의 출제 경향에 맞춰 연습량을 배분한다
- 문제 데이터베이스가 한 번 만들고 끝나는 것이 아니라 지속적으로 늘어날 수 있는 구조를 갖춘다
- 개인 프로젝트로 시작하되, 다른 사람도 같은 링크로 각자 설정해 쓸 수 있게 한다

### 성공 지표 (제안)
- 알림을 받은 날 중 실제로 문제를 열람/풀이 체크한 비율
- 연속 알림 수신·확인 일수(스트릭)
- "건너뛰기" 대비 "풀었음 체크" 비율 (문제 적합도 지표)
- 문제 제안 PR 누적 수 및 병합률

## 4. 타겟 사용자
- 주 사용자: 특정 기업 코딩테스트를 준비하는 개인(본인, 코드스쿼드 등 부트캠프 수강생 포함)
- 확장 사용자: 같은 목적으로 취업을 준비하는 지인·커뮤니티 — 로그인 없이 링크만으로 각자 독립적인 설정을 가질 수 있음

## 5. 범위

### In scope
- iOS(및 Web Push를 지원하는 모든 브라우저)에서 홈 화면 추가형 PWA로 동작
- 사용자별 알림 스케줄(시간/요일/일시정지), 문제 범위 필터(기업/태그/난이도), 출제 순서(순차·랜덤·안 푼 우선) 설정
- 오늘의 문제 열람, 건너뛰기, 알림 재발송, 풀이 여부 체크, 진행 기록 초기화
- 문제 데이터 영속 저장(Postgres) 및 신규 문제 제안 → GitHub PR 자동 생성
- 무료 티어 인프라(Render, Neon, GitHub Actions/cron-job.org)로 배포 가능한 구조

### Out of scope (현재 버전 기준)
- 로그인/계정 시스템 (브라우저 기반 익명 clientId로 대체)
- 문제 자동 채점/코드 실행 환경 (문제 링크로 외부 플랫폼 이동해 풀이)
- PR 자동 병합(항상 사람이 검토 후 병합)
- Android 전용 네이티브 푸시 최적화(웹 표준 Push API만 사용)
- 통계 대시보드(스트릭, 완료율 시각화 등)

## 6. 기능 요구사항

### 6.1 알림 스케줄
- 알림 시간을 분 단위로 지정 가능
- 알림 요일을 요일별로 선택 가능(예: 평일만)
- 하루 발송 문제 수 1~3개 선택 가능
- 일시정지: 즉시 끄기 또는 특정 날짜까지 정지, 해당 날짜 경과 시 자동 해제
- 서버는 15분 주기로 깨워져 "지금 발송 대상인 사용자"를 판별해 발송(사용자별 임의 시간 지원을 위함)
- 이미 오늘 발송된 사용자에게는 중복 발송하지 않음

### 6.2 문제 범위 및 출제 로직
- 기업 필터(다중 선택, 미선택 시 전체)
- 알고리즘 태그 필터(다중 선택)
- 난이도 필터(다중 선택)
- 출제 순서: 순차적(날짜 기반 로테이션) / 랜덤(날짜+사용자 시드 기반 결정론적 랜덤) / 안 푼 문제 우선
- 필터 조건에 맞는 문제가 없을 경우 전체 문제 중에서 대체 선택

### 6.3 오늘의 문제 상호작용
- 오늘의 문제 열람(문제명, 플랫폼, 난이도, 태그, 링크, 자체 작성 요약 — 원본 문제 페이지를 스크래핑/임베드하지 않고 앱 안에서 직접 작성한 요약으로 표시)
- 건너뛰고 다른 문제로 교체
- 알림 다시 보내기(수신 확인/테스트 용도)
- 풀었음 체크 → "안 푼 문제 우선" 모드에 반영
- 푼 문제 기록 전체 초기화

### 6.4 문제 데이터 관리
- 문제 데이터는 `id, company, name, plat, level, tags, url, exp` 필드를 가진 레코드로 관리
- 신규 문제는 사이트의 "문제 제안하기" 폼으로 제출 가능(완전 공개, 접근 제한 없음)
- 제출 시 서버가 GitHub API로 새 브랜치 생성 → `problems.json` 수정 커밋 → PR 자동 생성
- 저장소 소유자가 PR을 검토·병합해야 실제 반영(자동 병합 없음)

### 6.5 알림 인프라 (PWA/Web Push)
- iOS 16.4+ 홈 화면 추가 PWA에서 Web Push 수신
- 서비스 워커가 푸시 수신 및 알림 클릭 시 앱 진입 처리
- 알림 활성화 시 브라우저 Push 구독 정보를 서버에 등록

## 7. 비기능 요구사항
- **가용성**: 무료 호스팅(Render) 기준 서비스 슬립/재기동에 따른 30~50초 지연 허용
- **데이터 영속성**: 사용자 설정·진행 상태는 Postgres(Neon 등)에 저장하여 재배포/재시작에도 유지. DB 미설정 시 로컬 파일로 폴백(개발용)
- **확장성**: 사용자 수 증가 시에도 사용자별 설정이 독립적으로 저장되도록 clientId 기반 구조 사용
- **보안**: 크론 발송 엔드포인트는 시크릿 키로 보호. GitHub PR 생성은 저장소 범위로 제한된 Fine-grained PAT 사용
- **비용**: 전체 스택을 무료 티어(Render Web Service, Neon Postgres, GitHub Actions 또는 cron-job.org)로 운영 가능해야 함
- **알림 지연 허용치**: 목표 시각 대비 최대 30분 이내 발송 보장(폴링 주기 및 무료 크론 서비스 지연 고려)

## 8. 시스템 아키텍처 개요
```
[iOS 홈 화면 PWA] --Web Push 구독--> [Express 서버 (Render)]
                                         |-- storage.js --> [Postgres (Neon)]
                                         |-- github-suggest.js --> [GitHub API: 브랜치/커밋/PR]
                                         |-- web-push --> [Push 서비스] --> [기기 알림]
[GitHub Actions / cron-job.org] --15분마다 POST /api/send-daily--> [Express 서버]
```
- **server.js**: 라우팅, 스케줄 판정, 문제 선택 로직, 푸시 발송
- **storage.js**: 구독자(설정/진행상태/구독정보) 저장소 추상화 — `DATABASE_URL` 존재 시 Postgres, 없으면 로컬 JSON 파일
- **github-suggest.js**: 문제 제안 → GitHub 브랜치 생성/커밋/PR 생성
- **public/**: PWA 프론트엔드(설정 UI, 오늘의 문제, 문제 제안 폼, 서비스 워커, 매니페스트)

## 9. 데이터 모델

### 9.1 문제 (`data/problems.json`, git 관리)
| 필드 | 설명 |
|---|---|
| id | 고유 식별자 (slug) |
| company | 기업(군) |
| name | 문제명 |
| plat | 플랫폼(프로그래머스/백준 등) |
| level | 난이도 |
| tags | 알고리즘 태그(쉼표 구분 문자열) |
| url | 문제 링크(실제 풀이·채점은 원본 사이트로 이동) |
| exp | 자체 작성 문제 요약 — 핵심 아이디어, 예시 입출력, 접근법 해설 등을 직접 작성. 원본 문제 본문을 그대로 복제하지 않음(저작권 문제 회피) |

### 9.2 구독자 (Postgres `subscribers` 테이블 / 파일 폴백)
| 필드 | 설명 |
|---|---|
| client_id | 브라우저별 익명 식별자(PK) |
| subscription | Web Push 구독 정보(JSONB, 미가입 시 NULL) |
| settings | 알림 시간/요일/일수/일시정지/필터/순서 (JSONB) |
| solved_ids | 풀었음 체크한 문제 id 목록 (JSONB) |
| state | lastSentDate, skipSeed, skipDate 등 내부 진행 상태 (JSONB) |

## 10. 주요 사용자 흐름
1. **최초 설정**: 사이트 접속 → 알림 시간/요일/기업/태그/난이도/순서 설정 → 저장 → "알림 켜기"로 Push 구독 → 홈 화면에 추가
2. **일일 알림 수신**: 설정 시각 도달 → 서버가 오늘의 문제 계산 → Push 발송 → 알림 클릭 시 앱 진입 → 오늘의 문제 확인
3. **문제 교체**: 오늘의 문제가 마음에 안 듦 → 건너뛰기 → 동일 조건에서 다른 문제로 즉시 교체
4. **풀이 기록**: 문제 풀이 후 "풀었음" 체크 → 이후 "안 푼 문제 우선" 모드에 반영
5. **문제 제안**: 새로운 기출/연습 문제 발견 → 제안 폼 제출 → GitHub PR 자동 생성 → 저장소 소유자 검토/병합 → 다음 배포에 반영

## 11. API 요약
| Method | Path | 설명 |
|---|---|---|
| GET | /api/meta | 기업/태그/난이도 목록, 제안 기능 활성화 여부 |
| GET | /api/settings | 사용자 설정/진행 상태 조회(없으면 기본값 생성) |
| POST | /api/settings | 설정 저장 |
| POST | /api/subscribe / /api/unsubscribe | Push 구독 등록/해제 |
| GET | /api/today | 오늘의 문제(개인 설정 반영) |
| POST | /api/skip-today | 오늘의 문제 재선정 |
| POST | /api/resend-today | 오늘의 알림 재발송 |
| POST | /api/mark-solved / /api/reset-progress | 풀이 기록 관리 |
| POST | /api/suggest-problem | 문제 제안 → GitHub PR 생성 |
| POST | /api/send-daily | (크론 전용) 발송 대상 판정 및 일괄 발송 |

## 12. 제약사항 및 리스크
- **iOS 버전 제약**: 16.4 미만 기기는 Web Push 미지원 — 알림 기능 자체가 동작하지 않음
- **무료 호스팅 한계**: Render 무료 웹 서비스의 슬립/재기동, Neon의 유휴 시 슬립 등으로 인한 지연 가능성
- **크론 정확도**: GitHub Actions 무료 스케줄은 트래픽에 따라 지연될 수 있어, 목표 시각 대비 최대 30분의 허용 오차를 둠
- **제안 폼 어뷰징**: 완전 공개형이라 스팸/부적절한 제안이 들어올 수 있음 — PR 검토·병합 단계에서 사람이 필터링
- **콘텐츠 신뢰도**: 각 기업 코딩테스트 경향은 공개 후기 기반으로 조사된 것으로, 실제 출제와 다를 수 있음(사용자에게 참고용임을 안내 필요)
- **저작권**: 원본 문제 페이지를 스크래핑하거나 iframe으로 무단 임베드하지 않는다. `exp` 필드는 항상 자체 작성 요약이며, 실제 원문·채점은 `url`을 통해 원본 사이트로 이동해서 진행한다
- **외부 플랫폼 가용성**: 백준(BOJ)이 2026-04-28부로 서비스를 종료(재개 예정 안내만 있는 상태)해 현재 `problems.json`은 프로그래머스·리트코드 문제로 구성되어 있음. 문제 링크는 작성 시점에 실제 접속해 존재를 확인한 것만 등록하며(기억에 의존한 링크 작성 금지), 백준 등 특정 플랫폼이 중단될 경우를 대비해 플랫폼을 다양화하기보다 "그 시점에 실제로 살아있는 플랫폼" 기준으로 문제를 채운다
- **개별 문제 직링크 가능 여부**: 코드시그널·코드트리는 로그인 없이 개별 문제를 바로 가리키는 공개 URL 구조를 확인하지 못해(코드시그널은 계정/기업 평가 중심, 코드트리는 로그인 후 접근하는 Trail 학습 구조) 현재 범위에서 제외. 로그인 후 URL 구조가 고정되는 것이 확인되면 재검토

## 13. 향후 로드맵 (제안)
- 통계 대시보드: 스트릭, 기업별/태그별 풀이 현황 시각화
- 문제 수 확충: 커뮤니티 제안 PR을 통한 지속적 콘텐츠 확장
- 다중 알림 채널: 이메일/카카오톡 알림 등 대체 채널 추가 검토
- 난이도 자동 조정: 풀이 소요 시간/정답 여부 기반 추천 고도화
- 관리자 화면: PR 검토 없이도 신뢰도 높은 제안을 빠르게 반영할 수 있는 간단한 승인 플로우

## 14. 오픈 이슈
- 성공 지표를 실제로 측정하려면 "풀이 완료" 신호를 어떻게 수집할지 정의 필요(현재는 자기 체크 기반)
- 문제 제안 폼에 악의적 제출이 몰릴 경우 대비책(속도 제한 등) 필요 여부 재검토
- 다중 알림 채널 확장 시 사용자 식별 방식(현재 익명 clientId)을 계정 기반으로 전환할지 여부

## 15. 프로젝트 진행 방식

### 15.1 원칙
- **프로젝트명/작업 폴더 고정**: 프로젝트명은 "코딩테스트 데일리", 작업 폴더는 `Project/` 하위로 고정하고 이 안에서만 구현을 진행한다
- **PRD 우선 작성**: 구현에 착수하기 전 본 PRD로 요구사항과 범위를 먼저 확정한다. 코드 작성 중 요구사항이 바뀌면 코드보다 PRD를 먼저 갱신한다
- **단계적 구현**: 모든 기능을 한 번에 구현하지 않는다. 핵심 기능(오늘의 문제를 조회하는 최소 동작)을 먼저 만들어 동작을 확인한 뒤, 그 위에 설정·알림·자동화·데이터 영속성 순으로 기능을 쌓는다
- **TODO 기반 추적**: 아래 15.2 단계별 목록을 [TODO.md](TODO.md)에 체크리스트(칸반형 To do/In Progress/Done)로 옮겨 관리하고, 각 항목을 구현·검증할 때마다 하나씩 완료 처리한다

### 15.2 단계별 구현 순서 (Phase)
각 Phase는 이전 Phase가 "실제로 동작하는 것"을 확인한 뒤에만 다음으로 넘어간다.

| Phase | 내용 | 관련 요구사항 |
|---|---|---|
| 0 | 프로젝트 셋업: 폴더/레포 구조, package.json, 기본 서버 스캐폴딩 | §8 |
| 1 | 핵심 MVP: 정적 `problems.json` + 알림 없이 오늘의 문제를 웹에서 조회 (날짜 기반 로테이션만) | §6.2(순차), §9.1, §11 GET /api/today |
| 2 | 사용자별 설정: clientId 발급, 기업/태그/난이도 필터, 출제 순서(순차·랜덤·안 푼 우선) | §6.2, §9.2, §11 GET/POST /api/settings |
| 3 | 오늘의 문제 상호작용: 건너뛰기, 풀었음 체크, 기록 초기화 | §6.3, §11 skip/mark-solved/reset-progress |
| 4 | 데이터 영속성: storage.js 추상화 → 로컬 파일 폴백 → Postgres(Neon) 연동 | §7 데이터 영속성, §9.2 |
| 5 | PWA/Web Push 인프라: manifest, 서비스 워커, 홈 화면 추가, 구독/해제 | §6.5, §11 subscribe/unsubscribe |
| 6 | 알림 스케줄링 자동화: 시간/요일/일시정지 판정, 15분 주기 크론 발송, 중복 발송 방지 | §6.1, §11 send-daily |
| 7 | 문제 제안 → GitHub PR 자동화: 제안 폼, github-suggest.js, PAT 연동 | §6.4, §11 suggest-problem |
| 8 | 배포 및 운영: Render/Neon/GitHub Actions 무료 티어 배포, 환경변수·시크릿 설정, 종단 테스트 | §7 비용/보안, §12 |
| 9+ | (향후) 통계 대시보드, 다중 알림 채널, 난이도 자동 조정, 관리자 승인 플로우 | §13 향후 로드맵 |

Phase 0~3까지가 "알림 없이 브라우저에서 개인화된 오늘의 문제를 보고 풀이 여부를 기록하는" 핵심 루프이며, 이 범위가 먼저 동작해야 Phase 4 이후(영속성·푸시·자동화·PR 연동)로 확장한다.

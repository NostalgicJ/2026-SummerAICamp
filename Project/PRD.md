# PRD: 알고핑 (AlGoPing)

## 1. 개요
목표 기업(네이버, 카카오, 쿠팡·배민·당근·토스, 삼성·현대·SK)의 코딩테스트 출제 경향에 맞춘 대표 문제를 매일 웹 푸시 알림으로 받아보고, 아이폰 홈 화면에서 앱처럼 사용할 수 있는 PWA(Progressive Web App)이다. 사용자별로 알림 시간, 요일, 기업/알고리즘/난이도 필터, 출제 순서를 자유롭게 설정할 수 있고, 새 문제는 GitHub PR을 통해 검토 후 반영하는 방식으로 여러 사람이 함께 채워나갈 수 있다.

## 2. 배경 및 문제 정의
코딩테스트는 기업마다 자주 나오는 유형과 평가 포인트가 다르다. 목표 없이 무작위로 문제를 풀면 실제 시험에서 낯선 유형에 시간을 뺏기거나, 정작 자주 나오는 유형에 대한 숙련도가 부족한 채로 시험에 임하게 된다. "매일 한 문제씩 꾸준히 푼다"는 계획은 세우기는 쉬워도 실천이 어렵고, 기존 코딩테스트 연습 서비스들은 알림을 특정 시간에 개인화해서 보내주거나 기업별 경향에 맞춰 문제를 골라주지 않는다.

2026-07-27 페르소나 인터뷰(3인, 방법·근거는 §16 참고)를 거치며 위 배경을 아래 4개의 더 구체적인 하위 문제로 나눠 검증했다.

- **문제 정의 A — 선택 자체가 병목이다**: 실력이 부족한 게 아니라, "오늘 뭘 풀지" 정하는 과정(유형 분류, 기업별 경향 조사, 정리)에서 시간을 다 써버려 정작 문제를 풀 시간이 남지 않는다. 완벽주의 성향이 강할수록 이 병목이 더 크다.
- **문제 정의 B — 알림을 확인해도 실행으로 이어지지 않는다**: 애초 가정("알림이 오면 바로 반응한다")과 달리, 알림을 열어보는 것과 실제로 문제를 풀기 시작하는 것 사이엔 별도의 저항이 있다. 감정 상태(자괴감, 무기력, 컨디션)에 따라 "이따 할게"로 미루고 그대로 하루가 끝나는 경우가 흔하다.
- **문제 정의 C — 큐레이션 없이는 방향성에 대한 확신이 없다**: 목표 기업 스타일에 맞춘 문제인지 여부가 단순한 선호가 아니라, "내가 지금 헛짓을 하고 있지 않다"는 심리적 안정감과 직결된다.
- **문제 정의 D — 동기부여 장치는 감정 상태에 좌우되는 조건부 효과다**: 스트릭·통계 같은 시각적 기록은 승부욕·완벽주의가 있는 사용자에게 강하게 작동하지만, 감정 기복이 큰 날에는 그 장치조차 무시되고 회피로 이어질 수 있다.

## 3. 목표
- 매일 정해진 시간에 목표 기업 유형에 맞는 문제를 놓치지 않고 받아본다
- 준비 중인 기업이 여러 곳이어도 각각의 출제 경향에 맞춰 연습량을 배분한다
- 문제 데이터베이스가 한 번 만들고 끝나는 것이 아니라 지속적으로 늘어날 수 있는 구조를 갖춘다
- 개인 프로젝트로 시작하되, 다른 사람도 같은 링크로 각자 설정해 쓸 수 있게 한다

### 성공 지표 (제안)
- 알림을 받은 날 중 실제로 문제를 열람/풀이 체크한 비율
- 연속 알림 수신·확인 일수(스트릭)
- "건너뛰기" 대비 "풀었음 체크" 비율 (문제 적합도 지표)
- 문제 제안 PR 누적 수 및 병합률

## 4. 타겟 사용자
- **주 사용자 (핵심 프로필)**: 알고리즘 기초 실력은 이미 있지만, 무엇을 풀지 정하는 결정 피로·완벽주의 때문에 꾸준한 실행이 어려운 코딩테스트 준비생(본인, 코드스쿼드 등 부트캠프 수강생 포함). 2026-07-27 페르소나 인터뷰 결과, 이 핵심 프로필은 특정 연령대·학력에 국한되지 않음을 확인함 — 4년제 졸업 직후 20대 중반(백엔드/서버 개발자 지망)뿐 아니라, 대학원 졸업 후 연구직을 노리는 20대 후반, 전문대 졸업 후 임베디드/산업단지 엔지니어를 노리는 30대까지 전부 동일한 핵심 문제(결정 피로 + 조건부 동기부여 반응성, §2 문제 정의 A·D)를 겪고 있었음. 즉 알고핑의 실제 타겟은 처음 정의했던 것보다 연령·학력·직군 면에서 더 넓다
- 확장 사용자: 같은 목적으로 취업을 준비하는 지인·커뮤니티 — 로그인 없이 링크만으로 각자 독립적인 설정을 가질 수 있음
- **범위 밖으로 명확히 한 대상**: 알고리즘 기초 개념 자체를 처음 배우는 완전 초보자 — 인터뷰한 페르소나 전원이 "실력은 있는데 실행이 안 되는" 유형이었고, 알고핑은 학습 콘텐츠 서비스가 아니라 "이미 할 수 있는 사람의 꾸준함"을 돕는 데 초점이 맞춰져 있음

## 5. 범위

### In scope
- iOS(및 Web Push를 지원하는 모든 브라우저)에서 홈 화면 추가형 PWA로 동작
- 사용자별 알림 스케줄(시간/요일/일시정지), 문제 범위 필터(기업/태그/난이도), 출제 순서(순차·랜덤·안 푼 우선) 설정
- 오늘의 문제 열람, 건너뛰기, 알림 재발송, 풀이 여부 체크, 진행 기록 초기화
- 문제 데이터 영속 저장(Postgres) 및 신규 문제 제안 → GitHub PR 자동 생성
- 무료 티어 인프라(Render, Neon, GitHub Actions/cron-job.org)로 배포 가능한 구조

### Out of scope (현재 버전 기준)
- 로그인/계정 시스템 (브라우저 기반 익명 clientId로 대체)
- 문제 자동 채점/코드 실행 환경 (문제 링크로 외부 플랫폼 이동해 풀이)
- PR 자동 병합(항상 사람이 검토 후 병합)
- Android 전용 네이티브 푸시 최적화(웹 표준 Push API만 사용)

## 6. 기능 요구사항

### 6.1 알림 스케줄
- 알림 시간을 분 단위로 지정 가능
- 알림 요일을 요일별로 선택 가능(예: 평일만)
- 하루 발송 문제 수 1~3개 선택 가능
- 일시정지: 즉시 끄기 또는 특정 날짜까지 정지, 해당 날짜 경과 시 자동 해제
- 서버는 15분 주기로 깨워져 "지금 발송 대상인 사용자"를 판별해 발송(사용자별 임의 시간 지원을 위함)
- 이미 오늘 발송된 사용자에게는 중복 발송하지 않음

### 6.2 문제 범위 및 출제 로직
- 기업 필터(다중 선택, 미선택 시 전체) — 각 기업 칩에 보유 문제 수를 `기업명 (N)` 형태로 함께 표시(`GET /api/meta`의 `companyCounts`를 매 요청마다 `problems.json`에서 다시 집계해 반환하므로 문제 추가/삭제가 그대로 반영됨, 2026-07-28)
- 알고리즘 태그 필터(다중 선택)
- 난이도 필터(다중 선택)
- 출제 순서: 순차적(날짜 기반 로테이션) / 랜덤(날짜+사용자 시드 기반 결정론적 랜덤) / 안 푼 문제 우선
- 필터 조건에 맞는 문제가 없을 경우 전체 문제 중에서 대체 선택

### 6.3 오늘의 문제 상호작용
- 오늘의 문제 열람(문제명, 플랫폼, 난이도, 태그, 링크, 핵심 포인트, 단계별 풀이 접근 — 원본 문제 페이지를 스크래핑/임베드하지 않고 앱 안에서 직접 작성한 설명으로 표시)
- 건너뛰고 다른 문제로 교체
- 알림 다시 보내기(수신 확인/테스트 용도)
- 풀었음 체크 → "안 푼 문제 우선" 모드에 반영
- 푼 문제 기록 전체 초기화

### 6.4 문제 데이터 관리
- 문제 데이터는 `id, company, name, plat, level, tags, url, keyPoint, approach` 필드를 가진 레코드로 관리
- 신규 문제는 사이트의 "문제 제안하기" 폼으로 제출 가능(완전 공개, 접근 제한 없음)
- 제출 시 서버가 GitHub API로 새 브랜치 생성 → `problems.json` 수정 커밋 → PR 자동 생성
- 저장소 소유자가 PR을 검토·병합해야 실제 반영(자동 병합 없음)

### 6.5 알림 인프라 (PWA/Web Push)
- iOS 16.4+ 홈 화면 추가 PWA에서 Web Push 수신
- 서비스 워커가 푸시 수신 및 알림 클릭 시 앱 진입 처리
- 알림 활성화 시 브라우저 Push 구독 정보를 서버에 등록
- 서비스 워커가 앱 쉘(정적 파일)과 오늘의 문제 API 응답을 캐싱해, 오프라인 상태에서도 마지막으로 받아온 문제를 그대로 보여준다(네트워크 우선, 실패 시에만 캐시로 대체 — 캐시 우선 방식은 배포로 코드가 바뀌어도 사용자에게 옛 버전만 보이는 문제가 있어 배제)

### 6.6 통계 대시보드 및 화면 편의 기능
- 풀이 기록 페이지 상단에 통계 섹션 표시: 현재 연속 풀이일수(스트릭)·최고 기록·총 풀이 수, 최근 14주 잔디밭 스타일 캘린더 히트맵, 요일별 풀이 패턴, 태그별 풀이 분포
- 스트릭/캘린더/요일별 통계는 문제를 "풀었음" 체크한 날짜 기록(`solvedLog`)을 기반으로 계산 — 이 기능 도입 이전에 체크된 기록은 날짜를 알 수 없어 총 풀이 수·태그 분포에는 반영되지만 날짜 기반 통계에서는 자연히 제외됨
- 스트릭이 0일 때는 숫자를 그대로 보여주지 않고 "🌱 오늘부터 다시 시작해요"로 대체 — §16 인터뷰에서 확인된 "동기부여 장치가 감정 상태에 따라 회피를 유발할 수 있다"(문제 정의 D)는 점을 반영한 완화 장치
- 오늘의 문제 카드에 "💡 이 기업 코테 스타일로 골랐어요" 큐레이션 근거 문구 표시 — 문제 정의 C("큐레이션 없이는 방향성에 대한 확신이 없다") 대응
- 설정 페이지의 기업/태그/난이도/출제순서 필터는 "고급 설정"으로 기본 접힘(이미 설정해둔 사용자라도 항상 접힌 채로 시작) — 문제 정의 A("선택 자체가 병목이다") 대응, 알림 스케줄의 "일시정지"도 자주 안 쓰는 설정이라 같은 방식으로 접어둠
- PC/모바일 레이아웃 강제 전환 버튼: 실제 화면 폭과 무관하게 사용자가 고른 레이아웃을 유지(로컬 저장). 저장된 선택이 없으면 화면 폭 기준으로 자동 결정
- 첫 방문 시 1회성 온보딩 코치마크: 탭 구성, PC/모바일 전환, 알림 켜는 법을 짧게 안내하고 이후 다시 띄우지 않음

### 6.7 CS 개념 사전
- 알고리즘 탭과 동급인 5번째 상단 탭("CS 개념")으로 제공 — 문제 풀이와 연결되지 않는 순수 정보 제공용
- 운영체제·네트워크·데이터베이스·객체지향/설계 등 코딩테스트 이후 면접에서 자주 나오는 CS 기초 개념을 자체 작성 설명으로 제공(원본 교재/자료를 그대로 옮기지 않음)
- 알고리즘 탭과 동일한 "칩 선택 → 아래 아코디언 카드 자동 펼침" 상호작용을 따름(개념별 이미지는 아직 없음 — 필요 시 추후 추가 가능)

## 7. 비기능 요구사항
- **가용성**: 무료 호스팅(Render) 기준 서비스 슬립/재기동에 따른 30~50초 지연 허용
- **데이터 영속성**: 사용자 설정·진행 상태는 Postgres(Neon 등)에 저장하여 재배포/재시작에도 유지. DB 미설정 시 로컬 파일로 폴백(개발용)
- **확장성**: 사용자 수 증가 시에도 사용자별 설정이 독립적으로 저장되도록 clientId 기반 구조 사용
- **보안**: 크론 발송 엔드포인트는 시크릿 키로 보호. GitHub PR 생성은 저장소 범위로 제한된 Fine-grained PAT 사용
- **비용**: 전체 스택을 무료 티어(Render Web Service, Neon Postgres, GitHub Actions 또는 cron-job.org)로 운영 가능해야 함
- **알림 지연 허용치**: 목표 시각 대비 최대 30분 이내 발송 보장(폴링 주기 및 무료 크론 서비스 지연 고려)

## 8. 시스템 아키텍처 개요
```
[iOS 홈 화면 PWA] --Web Push 구독--> [Express 서버 (Render)]
                                         |-- storage.js --> [Postgres (Neon)]
                                         |-- github-suggest.js --> [GitHub API: 브랜치/커밋/PR]
                                         |-- web-push --> [Push 서비스] --> [기기 알림]
[GitHub Actions / cron-job.org] --15분마다 POST /api/send-daily--> [Express 서버]
```
- **server.js**: 라우팅, 스케줄 판정, 문제 선택 로직, 푸시 발송
- **storage.js**: 구독자(설정/진행상태/구독정보) 저장소 추상화 — `DATABASE_URL` 존재 시 Postgres, 없으면 로컬 JSON 파일
- **github-suggest.js**: 문제 제안 → GitHub 브랜치 생성/커밋/PR 생성
- **public/**: PWA 프론트엔드(설정 UI, 오늘의 문제, 문제 제안 폼, 서비스 워커, 매니페스트)

## 10. 주요 사용자 흐름
1. **최초 설정**: 사이트 접속 → 알림 시간/요일/기업/태그/난이도/순서 설정 → 저장 → "알림 켜기"로 Push 구독 → 홈 화면에 추가
2. **일일 알림 수신**: 설정 시각 도달 → 서버가 오늘의 문제 계산 → Push 발송 → 알림 클릭 시 앱 진입 → 오늘의 문제 확인
3. **문제 교체**: 오늘의 문제가 마음에 안 듦 → 건너뛰기 → 동일 조건에서 다른 문제로 즉시 교체
4. **풀이 기록**: 문제 풀이 후 "풀었음" 체크 → 이후 "안 푼 문제 우선" 모드에 반영
5. **문제 제안**: 새로운 기출/연습 문제 발견 → 제안 폼 제출 → GitHub PR 자동 생성 → 저장소 소유자 검토/병합 → 다음 배포에 반영

## 12. 제약사항 및 리스크
- **iOS 버전 제약**: 16.4 미만 기기는 Web Push 미지원 — 알림 기능 자체가 동작하지 않음
- **무료 호스팅 한계**: Render 무료 웹 서비스의 슬립/재기동, Neon의 유휴 시 슬립 등으로 인한 지연 가능성
- **크론 정확도**: GitHub Actions 무료 스케줄은 트래픽에 따라 지연될 수 있어, 목표 시각 대비 최대 30분의 허용 오차를 둠
- **제안 폼 어뷰징**: 완전 공개형이라 스팸/부적절한 제안이 들어올 수 있음 — PR 검토·병합 단계에서 사람이 필터링
- **콘텐츠 신뢰도**: 각 기업 코딩테스트 경향은 공개 후기 기반으로 조사된 것으로, 실제 출제와 다를 수 있음(사용자에게 참고용임을 안내 필요)
- **저작권**: 원본 문제 페이지를 스크래핑하거나 iframe으로 무단 임베드하지 않는다. `keyPoint`/`approach` 필드는 항상 자체 작성 설명이며, 실제 원문·채점은 `url`을 통해 원본 사이트로 이동해서 진행한다
- **외부 플랫폼 가용성**: 백준(BOJ)이 2026-04-28부로 서비스를 종료(재개 예정 안내만 있는 상태)해 현재 `problems.json`은 프로그래머스·리트코드 문제로 구성되어 있음. 문제 링크는 작성 시점에 실제 접속해 존재를 확인한 것만 등록하며(기억에 의존한 링크 작성 금지), 백준 등 특정 플랫폼이 중단될 경우를 대비해 플랫폼을 다양화하기보다 "그 시점에 실제로 살아있는 플랫폼" 기준으로 문제를 채운다
- **개별 문제 직링크 가능 여부**: 코드시그널·코드트리는 로그인 없이 개별 문제를 바로 가리키는 공개 URL 구조를 확인하지 못해(코드시그널은 계정/기업 평가 중심, 코드트리는 로그인 후 접근하는 Trail 학습 구조) 현재 범위에서 제외. 로그인 후 URL 구조가 고정되는 것이 확인되면 재검토

- **단계적 구현**: 모든 기능을 한 번에 구현하지 않는다. 핵심 기능(오늘의 문제를 조회하는 최소 동작)을 먼저 만들어 동작을 확인한 뒤, 그 위에 설정·알림·자동화·데이터 영속성 순으로 기능을 쌓는다
- **TODO 기반 추적**: 아래 15.2 단계별 목록을 [TODO.md](TODO.md)에 체크리스트(칸반형 To do/In Progress/Done)로 옮겨 관리하고, 각 항목을 구현·검증할 때마다 하나씩 완료 처리한다

## 16. 사용자 인터뷰 기반 검증 (2026-07-27)

### 16.1 방법
캠프 Day6-2(가상 사용자 인터뷰) 방식에 따라, 알고핑의 실제 타겟에 가까운 커스텀 페르소나를 설계하고 서브에이전트 3개에 각각 역할을 부여해 동일한 질문지로 독립 인터뷰를 진행했다.

- **차현우** (26세, 4년제, 서버 개발자 지망, 서울) — 캠프 예시 페르소나 "정재현"의 취준생 생활 디테일(계획은 세우되 막막하면 계획표만 고치며 하루를 흘려보내는 패턴)과, 캠프에서 제공된 페르소나 "고태윤"의 실제 개발 역량·기업 지망 설정을 섞어 알고핑 검증용으로 새로 설계
- **고태윤** (26세, 대학원 석사, AI 연구소 지망, 서울) — 캠프 제공 "전국 AI 관심 취준생 10인" 페르소나 중 발췌
- **강경래** (31세, 전문대, AI 산업단지 엔지니어 지망, 광주) — 위와 동일 출처에서 발췌. 완벽주의·나이 압박감이 있는 30대 프로필

### 16.2 검증한 가정
- A: 코딩테스트 준비생은 "오늘 어떤 문제를 풀지" 정하는 것 자체가 부담이라 실행을 미루게 된다
- B: 알림(푸시)이 오면 실제로 그 순간 문제를 확인하고 반응할 가능성이 높아진다
- C: 목표 기업에 맞춰 문제를 골라주는 게 아무 문제나 푸는 것보다 유의미하게 느껴진다
- D: 스트릭(연속 기록)이나 통계 같은 시각적 피드백이 꾸준함에 실제로 동기부여가 된다

### 16.3 확인한 사실
- 3명 모두 문제를 고르는 데만 20분~2시간을 쓰고, 그러다 정작 하나도 못 풀고 하루가 끝나는 경험이 있었다 → **A 강하게 확인**
- 알림을 확인은 바로 해도 실제로 풀기 시작하는 건 미루는 경우가 많았다(확인≠착수) → **B는 부분 기각** — 원래 가정은 지나치게 단순화됐던 것으로 판명되어 §2 문제 정의 B로 재정의
- 3명 모두 목표 기업 스타일에 맞춘 문제를 아무 문제나 푸는 것보다 훨씬 의미있게 느낀다고 답함 → **C 강하게 확인**
- 스트릭·통계 기록이 있으면 끊기기 싫어서라도 계속 풀게 된다고 답했으나, 감정 기복이 큰 날엔 이마저 무시하고 회피하는 경우가 있었다 → **D는 조건부로 확인**(감정 상태에 좌우되는 효과)

### 16.4 이번 검증이 PRD에 반영된 곳
- §2 배경 및 문제 정의 — 단일 문단을 4개의 세분화된 하위 문제(A~D)로 분리
- §4 타겟 사용자 — 핵심 프로필을 "결정 피로 + 조건부 동기부여 반응성"을 겪는 사람으로 재정의하고, 연령대·학력·직군이 달라도 동일 프로필이 반복됨을 반영해 대상을 넓힘. 반대로 "알고리즘 초보자"는 범위 밖임을 명시
- §13 향후 로드맵 — B가 부분 기각된 점을 "알림 클릭 시 마찰 없는 즉시 착수 UX" 개선 과제로 추가(우선은 문제 정의 갱신에 그치고, 실제 기능 변경은 별도 논의 후 진행)

## 17. 회사별 코딩테스트 경향 조사 · 문제 매칭 파이프라인 (2026-07-28, 2026-07-29 방식 전환)

### 17.1 목적
`data/problems.json`(실제 사용자에게 발송되는 문제)의 콘텐츠를 기업별로 확장하기 위한 **오프라인 리서치·큐레이션 워크플로우**. AI가 새 문제를 창작하지 않고, 검증된 문제풀(프로그래머스/SWEA/리트코드)에서 그 기업의 경향과 가장 비슷한 **실제 존재하는 문제**를 찾아 추천한다.

> **2026-07-29 방향 전환**: 최초 설계(2026-07-28)는 기출이 없을 경우 AI가 Python 레퍼런스 솔루션·테스트케이스까지 갖춘 오리지널 문제를 직접 창작하는 방식이었다. 이 방식으로 만든 7건은 전부 폐기했다 — 실제 검증된 플랫폼의 기존 문제를 매칭 추천하는 쪽이 저작권·품질 리스크가 훨씬 낮고, "이 회사가 실제로 낸 문제(기출)"와 "경향이 비슷해서 골라준 문제(경향문제)"를 명확히 구분할 수 있기 때문이다.

### 17.2 처리 순서
1. **기출 여부 확인**: 웹 검색으로 해당 기업의 실제 공개 코딩테스트 문제(기술 블로그 해설, 프로그래머스 기업 기출 코너 등)가 있는지 먼저 확인한다. 있으면 원문을 재작성하지 않고 "기출" 라벨 + 원문 링크 + 간단한 유형·난이도 소개만 기록한다(원문 인용 금지).
2. **경향 수집**: 후기 블로그·기업 공식 기술 블로그를 참고해 유형/난이도/문제 구성/스타일/최근 경향 변화를 요약한다(원문 인용 금지, 백준은 서비스 미복구+스크래핑 금지 정책상 소스에서 제외).
3. **검증된 문제풀에서 매칭 추천**: 2단계 경향과 가장 비슷한 유형·난이도의 **실제 존재하는 문제**를 프로그래머스(기업 기출 코너 포함)/SWEA(삼성 계열)/리트코드(해외 유형 참고용)에서 찾아 추천한다. 문제명·플랫폼·링크·매칭 근거(유형/난이도 기준 1~2줄)·태그를 함께 기록하며, 문제 원문은 절대 재작성하지 않고 항상 링크로 연결한다. 추천 전 WebFetch로 해당 문제 페이지가 실제로 존재하는지 반드시 확인한다.
4. **경향 기록**: 2단계 요약을 `trends/[기업명].md`에 조사일자·소스 링크·이전 기록 대비 변화와 함께 남긴다.

### 17.3 데이터 위치 및 분류 기준
- `trends/[기업명].md` — 기업별 경향 조사 기록 및 매칭 추천 근거(누적, 조사할 때마다 갱신)
- 매칭 추천 결과는 검증 즉시 `data/problems.json`에 직접 반영한다(별도 검수 대기열 없음 — 이미 실제 플랫폼에서 검증된 문제를 링크만 연결하는 것이라, 오리지널 창작 문제와 달리 정답·테스트케이스 정확성 리스크가 없기 때문). 다만 회사-경향 매칭이 실제로 적절한지는 사람이 가볍게 훑어봐도 좋다.
- **분류 기준(`source` 필드)**: `"기출"` = 그 회사가 실제로 낸 것으로 확인된 문제(예: 프로그래머스 "20XX KAKAO BLIND RECRUITMENT" 공식 태그 확인). `"경향문제"` = 실제로 존재하는 검증된 문제이지만, 그 회사가 낸 문제라는 근거는 없고 유형·난이도가 비슷해 매칭 추천한 것.

### 17.4 명명 규칙
- 파일명(`trends/*.md`)은 영어(로마자) 슬러그로 통일한다 — 예: `daangn-market.md`, `sk-hynix.md`
- `trends/*.md` 문서에서는 축약형이 아닌 전체 회사명을 쓴다 — 예: "당근" → "당근마켓", "배민" → "배달의민족", "삼성" → "삼성전자", "SK" → "SK하이닉스", "현대" → "현대오토에버"
- `data/problems.json`의 `company` 필드는 기존 배포된 필터·배지 UI와의 호환을 위해 기존 축약 라벨(SK/네이버/당근/배민/삼성/카카오/쿠팡/토스/현대)을 그대로 유지한다

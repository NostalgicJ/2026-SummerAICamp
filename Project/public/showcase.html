01 · WHY

왜 만들었나

코딩테스트는 기업마다 자주 나오는 유형과 평가 포인트가 달라요. 그런데 목표 없이 무작위로 문제를 풀면 실제 시험에서 낯선 유형에 시간을 뺏기게 되죠. "매일 한 문제씩 꾸준히 푼다"는 계획은 세우기는 쉬워도 지키기 어렵고, 기존 코딩테스트 연습 서비스들은 개인화된 알림도 기업별 문제 선별도 해주지 않았어요.

막연한 감으로 시작하지 않으려고, 가상 페르소나 3명(서버 개발자 지망 26세, AI 연구소 지망 대학원생 26세, 산업단지 엔지니어 지망 31세)을 대상으로 인터뷰를 진행해 아래 4가지 가정을 검증했어요.

A

"오늘 뭘 풀지" 정하는 것 자체가 부담이라 실행을 미루게 된다

✓ 강하게 확인 — 3명 모두 문제 고르는 데만 20분~2시간을 썼다
B

알림이 오면 그 순간 바로 반응해서 문제를 풀기 시작한다

△ 부분 기각 — 확인은 해도 착수는 미루는 경우가 흔했다
C

목표 기업에 맞춘 문제가 아무 문제나 푸는 것보다 유의미하게 느껴진다

✓ 강하게 확인
D

스트릭·통계 같은 시각적 기록이 꾸준함에 동기부여가 된다

△ 조건부 확인 — 감정 기복이 큰 날엔 이마저 무시됐다

누구에게, 어떤 경우에 쓸모있나

  • 주 사용자 — 알고리즘 기초 실력은 있지만 결정 피로·완벽주의 때문에 꾸준한 실행이 어려운 코딩테스트 준비생 (나이·학력·직군을 가리지 않음을 인터뷰로 확인)
  • 확장 사용자 — 같은 목적으로 취업을 준비하는 지인·커뮤니티. 로그인 없이 링크만으로 각자 독립적인 설정 가능
  • 이런 순간에 — 여러 기업을 동시에 준비할 때 경향별로 연습량을 배분하고 싶을 때, 매일 정해진 시간에 문제를 놓치지 않고 받아보고 싶을 때
  • 범위 밖 — 알고리즘 기초 개념을 처음 배우는 완전 초보자 (학습 콘텐츠가 아니라 "이미 할 수 있는 사람의 꾸준함"을 돕는 도구예요)

Phase 1 · 1주차
초안

백준 23개 + 프로그래머스 6개로 첫 문제 데이터셋을 구성했어요.

발견

백준이 2026-04-28부로 서비스를 종료한 것을 확인했어요.

조치

23개 전부 프로그래머스의 살아있는 문제로 교체하고, "링크는 실접속 확인 후에만 등록"이라는 원칙을 세웠어요.

기업 라벨이 전부 틀렸다는 걸 재검증 과정에서 발견했다

Phase 7.5b · 2주차
초안

회사별 경향에 맞는 오리지널 문제를 AI가 직접 창작하고, 기존 38개 문제엔 "이 회사 스타일"이라는 라벨을 붙여뒀어요.

발견

라벨을 실제 출처와 대조 재검증하던 중, "다트 게임"(현대 라벨)은 사실 카카오 2018 기출이고 "조이스틱"(삼성 라벨)은 네덜란드 NWERC 2010 문제였다는 걸 발견했어요. 라벨이 실제 출처와 무관하게 스타일만 보고 붙여진 것이었죠.

조치

AI 창작 방식 자체를 폐기(생성 문제 7건 삭제)하고, "실제 존재하는 문제를 경향에 맞춰 매칭 추천"하는 파이프라인으로 전면 전환했어요.

"겉보기엔 그럴듯한 라벨도, 근거를 다시 확인하지 않으면 틀린 채로 남는다는 걸 배웠어요."

일시정지 날짜 필드, 다섯 번을 고치고서야 진짜 원인을 찾았다

Phase 8.5 · 2주차
1차

iOS에서 날짜 필드가 패널 밖으로 튀어나온다는 피드백 → 안내 텍스트를 겹쳐 추가했지만 해결 안 됨.

2차

select 3개(년/월/일)로 통째로 교체했으나 "너무 못생겼다"는 피드백으로 되돌림.

3차

진짜 원인은 날짜 필드가 아니라 옆 버튼에 min-width가 빠져있던 flex 레이아웃 버그였다는 걸 발견해 수정.

4차

iOS 전용 placeholder를 추가했지만 실기기에서 여전히 튀어나옴.

5차

iOS 네이티브 date picker가 페이지 CSS 폭 자체를 무시하는 문제로 결론 — 세로 배치로 전환하고, 뒤늦게 발견한 CSS 캐스케이드 버그까지 고친 뒤 overflow:hidden 안전장치를 추가.

"같은 버그가 반복되는 것처럼 보여도, 매번 원인은 달랐어요. 증상만 보고 고치면 다음 라운드에서 또 만나게 되더라고요."

배포 직전에 발견한, 조용히 모든 구독을 날릴 뻔한 버그

Phase 8 · 2주차
문제

Web Push용 VAPID 키가 로컬 파일에만 저장되고 있었어요. Render 같은 배포 환경은 재시작 시 파일시스템이 초기화될 수 있어서, 배포할 때마다 키가 바뀌고 기존 사용자 구독이 전부 무효화될 뻔했어요.

조치

환경변수(VAPID_PUBLIC_KEY/VAPID_PRIVATE_KEY)를 우선 사용하도록 고치고, 없을 때만 로컬 파일로 폴백하게 만들었어요.

"we don't have access to your repo" — Render 자동배포가 안 걸린 이유

Phase 8.5 · 2주차
증상

Render 대시보드는 "Auto-Deploy: On Commit"으로 정상 표시되는데, push를 해도 배포가 자동으로 안 걸리고 매번 수동 배포를 눌러야 했어요.

발견

GitHub 저장소에 Render 웹훅 자체가 등록돼 있지 않았어요 — 대시보드 표시와 실제 연동 상태가 어긋나 있었던 거죠.

조치

Render의 GitHub 연동에 의존하는 대신, main push 시 Render Deploy Hook URL을 직접 호출하는 GitHub Actions 워크플로를 새로 만들어 우회했어요.

05 · LEARNED

배운 점

01

실접속·재검증 없이 "그럴듯한" 데이터를 그대로 믿으면 안 된다는 걸 두 번(백준 서비스 종료, 기업 라벨 오류) 겪고서야 몸으로 익혔어요. 이후 원칙으로 문서화했어요.

02

같은 버그가 반복돼도 원인은 매번 다를 수 있어요. 일시정지 날짜 필드처럼, 증상이 같다고 지난번 해결책을 그대로 다시 쓰면 또 실패해요.

03

대시보드 표시(Auto-Deploy: On)를 실제 동작과 동일시하면 안 된다는 것 — 겉으로 정상처럼 보여도 실제 연동 지점(웹훅)을 직접 확인해야 했어요.

04

페르소나 인터뷰로 "알림 확인 ≠ 실제 착수"라는, 처음 가정에 없던 마찰을 발견했어요. 기능을 먼저 만들기보다, 가정을 먼저 검증하는 게 방향을 덜 틀리게 해줬어요.
